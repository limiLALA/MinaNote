# GDB

直接执行编译构建命令时，go底层默认会进行内联优化

```shell
go build -o bin/metric-proxy ./cmd
```

如果需要对编译后的的目标程序进行gdb调试，则需要加上 `-gcflags=all="-N -l"` 指令来关闭内联优化，这样可以让运行时(runtime)中的函数变得更容易调试

```shell
go build -gcflags=all="-N -l" -o bin/metric-proxy ./cmd
```

## 问题

```shell
gdb --pid 11168 --batch --ex 'b git.woa.com/dr/metric-proxy/pkg/domain/summarizer.(*Summarizer).updateSummaryTask'
```

最近在对go服务使用gdb打断点，遇到了一些问题，想分享出来给大家参考一下，后续有类似使用场景的可以快速定位解决：

场景：在实际生产测试环境中，一般会使用自动化流水线的方式来构建和部署最新版本的服务，此时如果编译构建机与服务部署机器不是同一台，环境不一致，则会导致在使用gdb调试时，由于缺少源代码和编译时使用的go版本，从而提示类似下面的错误

```shell
117	/data/landun/workspace/metric-proxy/pkg/domain/sumarizer/summarizer.go: No such file or directory
```

解决：需要在部署机器上将源代码copy到原编译目录下，并安装编译时使用的go版本，才能进行gdb调试，这在cpp程序上是没有出现过的。

分析：具体原因暂时没有查到，一开始以为和go的内联优化有关系，但是关闭了内联优化后问题依然存在，如果有碰到过类似问题的可以交流下~

# Delve

delve是一个比gdb更适合golang程序的调试工具，可以通过goroutine命令查看程序中的goroutine，进一步查看函数调用链
